# 30.1 The harness takes any AdditionalText

## Goal
`GeneratorHarnessInput.AdditionalTexts` is `IReadOnlyList<AdditionalText>?`, and `HarnessAdditionalText` is a sealed class deriving from `AdditionalText`, so a test can pass any `AdditionalText` implementation to the harness.

## Touches
- `src/Haitch.Roslyn.Testing/GeneratorHarnessInput.cs`
- `src/Haitch.Roslyn.Testing/HarnessAnalyzerConfigOptions.cs`
- `src/Haitch.Roslyn.Testing/GeneratorHarness.cs`
- `tests/Haitch.Roslyn.Tests/Testing/HarnessAdditionalTextTests.cs` (new)
- Existing callers that stop compiling, but only to adapt them; list each one in the report.

## Acceptance
`.claude/check.sh` exits 0, including tests where:
- a custom `AdditionalText` subclass defined in the test, with its own path and text, reaches a generator through the harness, and the generator sees its text;
- per-file options keyed by that custom text's path reach the generator;
- `new HarnessAdditionalText(path, text)` still works, and `GetText()` returns the text with the path as given;
- `AssertCacheable` passes with a custom `AdditionalText`.

## Constraints
- `HarnessAdditionalText` keeps the constructor `(string path, string text)` and the `Path`/`Text` properties. It drops record semantics, so remove any `with`/deconstruction usages.
- Delete the internal `HarnessAdditionalTextFile` wrapper. The harness passes the given `AdditionalText` instances straight to the driver.
- Per-file option lookup still matches by `AdditionalText.Path`.
- Update the XML docs on `AdditionalTexts` and `HarnessAdditionalText`.
- TDD: behavioural red first, meaning the custom-subclass test fails before the type change; a build error is acceptable only if no behavioural red is possible, and the report must say why. Edit only with Rider MCP tools.

## Out of scope
- `UnreadableAdditionalText` (30.2).
- Migrating direct-driver tests (slice 31).

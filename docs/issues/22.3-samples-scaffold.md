# 22.3 Samples scaffold

## Goal
`samples/` contains a sample generator project and a sample test project in the solution, with one sample generator tested through `GeneratorHarness`.

## Touches
- `samples/Haitch.Roslyn.Samples/Haitch.Roslyn.Samples.csproj` (new)
- `samples/Haitch.Roslyn.Samples/HelloGenerator.cs` (new)
- `samples/Haitch.Roslyn.Samples.Tests/Haitch.Roslyn.Samples.Tests.csproj` (new)
- `samples/Haitch.Roslyn.Samples.Tests/HelloGeneratorTests.cs` (new)
- `Haitch.Roslyn.slnx`

## Acceptance
`.claude/check.sh` exits 0 and its test output includes `HelloGeneratorTests`.

## Constraints
- The generator project targets netstandard2.0, references `Microsoft.CodeAnalysis.CSharp` (central version, `PrivateAssets=all`) and compiles `src/Haitch.Roslyn/**/*.cs` as linked source, the same way `tests/Haitch.Roslyn.Tests` does.
- The test project uses TUnit, references the sample project as a normal project reference and `src/Haitch.Roslyn.Testing`.
- Both projects set `IsPackable=false`, so `dotnet pack` in CI and publish produces no sample packages.
- `HelloGenerator` uses `ForTypesWithAttribute` and the scoped writer; it exists to prove the wiring, so keep it under 60 lines.
- Red: the test fails against a generator that emits nothing.
- Package versions go in `Directory.Packages.props` only if a new package is needed (none expected); name it in the report if so.

## Out of scope
- Additional sample generators, README content, packaging samples.
